# C1—C3：隔离实现、后续顺序与验收条件

当前阶段范围已经收敛为行情、研究和人工观察，C3 真实账户对账不适用；下文 C3 是保留的扩展能力合同，不是当前交付阻断项。历史副本跨盘恢复、离线包与分批容量验收见 [当前离线验收](offline_observation_acceptance.md)。

## 适用范围

本实现只处理显式新建的隔离工作区；所有输入和输出必须在该工作区内，拒绝路径越界、链接和目录联接。
它不连接生产库、调度器或券商，不恢复旧 offsite、splitter、CSV/API 导入入口，也不接入当前页面的账户资格或业绩计算。
已有运行库、原始记录和发布目录不作为默认输入。不得把生产目录初始化成演练目录。

开发树中的 `tools/v2/isolated_capabilities.py` 是本轮新入口。没有修改发布包白名单或生产绑定。
`trade_system/v2/recovery.py` 的原单库恢复、`scripts/archive_legacy_tables.py` 的原表导出和 `artifact_retention.py` 的测试产物保留计划继续保持原职责。
新账本复用基础类型与文件锁，不修改旧账户表或纸面账。

## 顺序与依赖

| 顺序 | 当前实现 | 下一步所需条件 | 最终验收条件 |
|---|---|---|---|
| C1 完整恢复 | 声明范围内的文件清单、哈希、DuckDB/SQLite 结构与行数、人工事件文件和发布指针核验；新目录恢复 | 实际恢复对象清单、独立机器/异地介质、凭据保管负责人、约定 RPO/RTO、隔离配置重绑定与环境重建材料 | 在独立环境恢复真实批准范围；哈希/行数/业务值/引用闭合；人工记录可读；原发布页可离线查看；故障演练可恢复；RPO/RTO 实测不超约定目标；全过程不启动采集/训练/执行 |
| C2 容量治理 | `multi_source_kline` 有界日期分区复制、完成回执、验证后续跑、完整产品键联合读取、保留源数据 | 对应源库的有效恢复证据；真实数据规模、增长率、保存要求；冷存储载体与查询性能目标 | 每个分区行数/类型/完整键/业务值/哈希一致；重复执行无重复；中断重试不覆盖坏文件；热冷联合结果与基准不漏不重；冲突拒绝；容量与查询耗时达约定目标；源退役另行批准 |
| C3 真实反馈 | 原始文件、严格规范输入、版本链、现金/持仓核对、独立人工确认与失效状态 | 脱敏真实对账单及对应开闭仓/现金控制、券商字段与单位映射、真实交易日历、完整费用及支持事件范围 | 真实凭据逐笔对应；现金和股数差额为零，舍入政策有凭据；重复/迟到/撤销/部分成交/费用反例通过；修订使旧确认失效；缺失或未支持事件阻断认证；人工确认独立；不混入模拟业绩 |

**C1 是任何源数据退役的硬前置。** C2 当前只复制，磁盘占用会暂时增加，不会自动产生容量节省。
C3 的格式设计和模拟验证可以与 C2 并行推进，但新账本纳入恢复范围且真实对账通过之前，不发布真实业绩。
本机恢复证明不替代异地验收。用户尚未提供独立环境与运营时间目标，相关状态保持待验收；真实对账单在本阶段不适用，不填假目标或模拟达标结论。

## C1 恢复合同

恢复计划必须明确五个不重叠目录：`code`、`environment`、`workspace`、`raw_facts`、`databases`，以及一个不含密码的 `credential_custody_reference`。
`workspace` 包含原配置、`publication/current.json`、不可变 runs、人工 notes 和其原始证据。代码和环境目录应由准备者放入批准版本、依赖锁和环境重建说明；工具校验这些文件的保存，不执行其中程序或安装依赖。
所有未列入的外部引用、供应商权限、模型外部文件及配置路径重绑定需要清单逐项补齐，不能凭文件复制成功判完整业务范围已验收。

工具持有隔离工作区的句柄锁及工作区现有写者使用的锁顺序，复制数据库时保持原生只读连接；复制前后重新比对全量清单，发现 WAL、变更、损坏、缺件或忙锁拒绝封存。
人工记录除单文件哈希外，还调用实际业务读取规则核对判断、原始证据、复盘、观察计划、预测引用和修订父记录；缺内部引用不能封存为合格恢复。SQLite 中识别到反馈账本时，共用 C3 的双向引用、版本链和核对检查，不能以数据库结构正常替代业务完整性。
永久 `.guard` 保留在原位，不当作恢复的锁所有权；Git 缓存、Python 缓存及人工事件可重建索引不打包。
`.env` 和常见私钥文件拒绝入包。此文件名门禁不是完整的敏感信息扫描；准备者仍需按凭据清单检查其他配置并独立保管密钥。
恢复文件保持原字节，包括可能仍指向原路径的配置，因此恢复目录只作为离线证据，必须经过独立重绑定和激活审批后才能成为运行工作区。
没有任何自动启动、上传、计划任务注册、删除或覆盖操作。失败目录保留，使用新的恢复目录重试。

记录的 `elapsed_seconds` 仅为本次核验和本机恢复步骤耗时，不包括灾难发现、设备准备、取回备份或环境安装，不能当作完整 RTO。RPO 不能用备份文件修改时间推算，必须用已确认业务事实和恢复点比较。

## C2 归档合同

目前只覆盖 `multi_source_kline`，不能用它宣称所有数据产品都已完成容量治理。
键固定为日期、资产类型、代码、来源、复权；缺键、空键或重复键进入处置流程，不自动去重。
日期窗口为左闭右开，单次分区/联合读取预算为 100,000 行，单次联合读取最多 100 个分区；实际大规模吞吐和存储策略仍待数据规模验收。
归档前必须重新读取恢复包和恢复目录，并确认源库字节哈希被该恢复点覆盖。源库新增或修订后，应先形成新的恢复点。

归档分区按内容合同确定身份，完成回执最后写入；复制完但未封存时可重新核验同一个文件再封存。
新 JSON 凭据先在同目录暂存文件中写完并刷新，再以不可覆盖的原子操作发布；中断暂存文件保留。该行为依赖文件系统支持同目录硬链接，本机验证不等于异地文件系统已验收。
对旧版本已留下的半写 `completed.json`，普通重试仍拒绝。只有显式提供 `archive --damaged-receipt-sha256 <现场哈希> --repair-reason <原因>`，且恢复点、源库与 parquet 多重集重新核对一致后，才将坏凭据保留到该分区的 `failed-receipts` 并重新封存。有效已封存凭据不允许替换；坏 parquet 不允许借凭据修复绕过检查。
不完整或损坏的 parquet 保留并拒绝覆盖，不能仅凭目录存在判断成功。
热冷完全相同的业务行只返回一次；同一完整键数值不同则拒绝，不擅自选择“热库优先”掩盖修订。
联合读取现在必须提供 `--coverage`。先通过 `plan-coverage` 绑定有效恢复点、源库身份、明确日期窗口、列类型、行数、完整业务值摘要和分区目录。读取时重新核对实际恢复基准与每个分区回执，漏传、额外传入、缺文件、窗口不同、少行、多行或相同行数但数值不同均拒绝。归档目录中“现存文件的集合”不能自行充当完整目录。
覆盖证明只针对该恢复快照和查询范围，不认证供应商事实完整性或后续新增数据。部分冷分区可与热库共同覆盖基准，但空热库加不完整冷分区不能通过；合法空窗口必须由恢复基准证明确实为零。源数据更新或范围变化需新的恢复点及覆盖计划。计划文件和分区目录应纳入后续批准的恢复对象清单；本轮没有改生产恢复配置。
保留计划只给出保留源与归档的决定。具体保存时长、成本预算、查询延迟目标、源数据退役和生产读路径切换未获本轮授权。

## C3 反馈合同

入口接受 `stockdata_feedback_statement_v1` JSON 和单独的原始文件，两者通过 SHA-256 绑定。券商专属 CSV/PDF 解析器仍需依据真实样本设计；不要通过旧导入器绕过新合同。
JSON 明确账户标识、`synthetic`/`broker_export` 来源、区间、日历、期初/期末现金及股数、完整性/费用声明和事件列表。
金额按“分”、数量按整数；原始映射不能猜测单位。日历是声明材料，并非工具自行认证的官方日历。
事件明确稳定 ID、版本、前版本哈希、发生时间、交易日、类型、状态、委托号、证券、方向、数量和金额。

- 成交金额是独立费用之前的成交总额；费用单独记账，原始费用标识必须稳定，避免同笔费用使用不同 ID 重复导入。
- 支持成交、撤单、费用、现金转移。撤单本身不冲销既有成交；取消错误成交必须追加关联旧版本的 `void` 修订。
- 重复导入不增加事件；相同 ID/版本内容不同、缺前版本、跳版本、跨交易日更正、模拟/券商身份混用整批拒绝。
- 迟到修订保留原件、版本链和旧核对结果。旧结果会标为被替代，其人工确认失效；必须核对并明确确认新结果。
- 期初 + 成交/费用/转账与期末现金、股数核对。未列入本次声明但仍然有效的旧事件不会被静默删除，会阻断核对通过。
- 同一声明可以保留事件历史版本，但以每个事件的最高声明版本核对当前状态；声明有效集合与实际应用集合必须双向对应，作废状态也必须对应当前版本。不得把已被作废的旧有效版本漏算后仍标为核对一致。
- 公司行动、跨区间更正、融资融券、冻结/可卖数量、委托全生命周期、税费追缴、汇率和真实收益归因尚未建模。遇到这些材料须扩展合同与反例，不能遗漏后继续认证。
- `arithmetic_reconciled`、原件真实性、人工确认和实盘资格分别记录。`broker_export` 只是来源声明；本轮 `real_statement_acceptance` 和 `execution_ready` 始终为 false。

账本使用新的 SQLite 文件保留原始字节、声明、事件和回执；原业务 DuckDB/旧结果表不写入。人工确认入口只能由明确确认操作调用，测试操作者不是用户签字。
查看、导入、确认、恢复与报告复用同一关系完整性检查。声明到事件版本、事件到原声明、账户来源、原始字节、核对结果及确认均检查引用；缺失最新修订不能只标为旧结果失效后继续报告完整。单表最多 100000 条，单次声明引用和核对重放预算累计最多 1000000 项；超过预算拒绝，真实规模验收时再明确扩展策略。
确认在同一个 SQLite 写事务内完成验证和落账，其他写者不能在两者之间插入修订。新 v2 核对回执绑定全部当前事件版本，包括 void；仅修改作废事件的版本而不改变金额，也使旧确认失效。历史 v1 回执与确认保留，但显示“旧版回执待重新核对”，不能沿用；显式重新导入原材料生成 v2 核对结果后才可重新确认，不自动迁移或代签。
数据库内关系检查不能发现一组相互引用的历史记录被整体删除后留下的自洽子集；仍需独立保管的恢复清单或外部链头证据。原始材料真实性也不由自哈希证明。

## 使用与验收材料

使用开发解释器执行 `tools/v2/isolated_capabilities.py --root <新隔离目录> init`，先准备隔离输入，再逐项调用 `capture`、`restore`、`archive`、`plan-coverage`、`joint-read`、`import-feedback`、`inspect-feedback` 和 `report`。每个命令的必填参数见其 `--help`。
除了初始化目录，所有路径参数都必须是隔离目录内部的相对路径。`confirm-feedback` 需明确指定核对回执、操作者和原始文件哈希。
`report` 重新验证恢复文件、归档和账本后导出自包含 HTML；不会修改当前工作台或历史复盘页，不能从这个演练页面升级业务资格。
报告仅列出分区时明确显示“归档覆盖尚未核验”。同时提供 `--coverage` 和 `--source` 后，重新执行实际联合读取并通过基准检查，才显示覆盖核验行数；账本损坏时拒绝生成报告，普通差异和陈旧声明则展示阻断依据。

每一阶段的交付应保存：源码版本与已有修改基线、输入清单/哈希、原始回执、失败反例、完整回归、实页内容与交互检查、耗时/规模，以及未验证项。未完成项不能填“通过”。
生产迁移、源退役、发布绑定、调度和运营恢复继续作为独立授权步骤。
