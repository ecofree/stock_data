# stock_data 执行级人工交易助手 V2：完整改造方案

**方案版本：** 1.0 / 2026-09-09  
**项目：** ecofree/stock_data  
**固定审计与本次复核基线：** `78324ba622bf6c5fc6cbb736a490e5818788d824`  
**交付性质：** 架构与实施规格，不是已修改的程序，不是已验证盈利策略。  
**目标：** 保留数据资产，修正正确性，建立付费数据驱动的交易闭环，并用独立对照决定投入。

## 0. 先固定决策：这次到底改成什么

改造不是“全面重写”，也不是“先修51个问题、以后再想价值”。采取**受控替换核心 + 一条付费数据业务闭环 + 免费基线对照**。两个目标共同验收：工程可靠，且产品确实更有用。

第一版产品是人工确认的执行级助手：它给出带输入证据、失效条件、有效期、真实账户约束的交易计划，记录人工处理和实际结果。这里的“执行级”表示信息及约束足以支持受控决策，不代表保证成交、保证止损或保证收益。

| 决策 | 本方案固定选择 |
|---|---|
| 主要业务 | A股短线、题材、情绪结构；不扩展期货、期权等新资产 |
| 第一条闭环 | D日题材核心候选 → D+1竞价结果确认 → 开盘后条件计划 → 已有持仓管理 → 人工结果复盘 |
| 研发架构 | 模块化单体，单写者服务；不先引入微服务、消息集群或图数据库 |
| 存储 | 保留DuckDB分析能力；独立v2 live库与离线research库，研究读取已发布快照，不直接读正在写的live文件 |
| KPL价值 | 题材原因/角色/梯队与经实测支持的过程证据，不把所有字段压为一个总分 |
| TuShare价值 | 历史样本、证券生命周期、复权、专题基准和风险事件，不假定盘后接口为实时 |
| 免费数据 | 保留为基础和对照，不因费用低就认为可靠，也不因已经花钱就强制付费源优先 |
| 模型 | 语义整理与影子研究；账户、时点、单位、数量、硬风控由确定性程序负责 |
| 委托接口 | 首期不自动下单；只读账户优先；受控券商写入为WP19独立、默认禁用扩展 |
| 交易参数 | 本方案不虚构收益有效阈值、账户风险预算和源TTL；必需参数未批准时只影子/研究 |

之前审计的主要证据是：累计资金语义冲突、覆盖式信号历史、零仓位风控、多处ready判定、回测重叠资金结算和Qlib实验缺陷。项目已有来源、事务、报告暂存和测试资产，不应笼统认定“一无是处”。具体问题性质与原验收条件完整保存在 `audit_traceability.json`。[A1]

## 1. 验收对象从“项目功能”改成“交易问题”

一个接口的使用层级必须分开统计：权益存在、取数成功、正确入库、被特征消费、影响决策或风险、被验证有价值。HTTP成功或表里有行最多证明前半部分。

最终作战卡必须回答：为什么关注该股而非同题材其他股；为何现在而非更早/更晚；什么条件否决；账户最多允许多少；买入后如何管理及哪些动作目前不能执行；依据是否有可比较样本。

数据产品必须绑定以下至少一种有意义的消费者：候选发现、条件触发、失效/否决、仓位与风险约束、已有持仓监控、历史验证、运行恢复。不强求每个来源直接改变买入名单，稳定性和节省操作成本也有价值。

**禁止以调用量、表数量、特征数量、报告页数或高分候选数量作为本轮成功指标。** 每个工作包都有一个用户可见或可核验的价值交付物。

## 3. 目标运行架构与存储所有权

```text
Windows任务 / CLI / 本地界面
                 │ 命令与查询，不直接写DB
                 ▼
         单一 stock_data service
       ┌───────────────────────────────┐
网络工作者 → 有界批次/耐久spool → 校验/提交者
       │ 事实/PIT → 特征 → 模式状态机   │
       │ 账户/对账 → 风险 → 统一决策记录 │
       │ 人工动作/结果 → 持仓管理       │
       └───────────────────────────────┘
            │              │
      v2 live.duckdb      原始档案/不可变manifest
            │              │
       当前投影          发布快照/Parquet
            │              ▼
       作战卡/告警    独立research.duckdb
                      重放/对照/Qlib
```

### 3.1 明确选用DuckDB的边界

本方案使用其嵌入式原生文件模式：一个进程拥有活动文件的读写；同进程内部再按单一提交者顺序化关键交易。外部UI/CLI通过服务查询，研究读取已发布的不可变导出。不能一边写原生文件、一边用独立进程read_only连接假设天然兼容。DuckDB官方明确区分单进程读写与多进程只读的模式；其他客户端/服务器方案不是本轮默认依赖。[S6]

网络等待、提供者重试、长模型调用不得持有数据库事务。历史回填写研究区/耐久批次，由服务在预算内接纳；不能与账户确认争夺长时间全库锁。第一版只承诺实测满足的分钟/人工决策能力，不宣称满足高频撮合。

### 3.2 原始字节与事务

原始响应先写临时对象、完成写入和hash校验再原子落档，随后数据库事务登记引用与标准化事实。中途崩溃可以留下未引用对象，但不能提交指向缺失字节的事实。未引用对象由延后GC清理，不能按年龄直接删除仍被决策引用的证据。

信号、决策证书、风险额度预占和outbox意图在同一活动库的短事务内提交。外部实际调用不能与本地事务视为一个原子事务；提交未知必须对账，不能承诺网络端到端exactly once。

### 3.3 明确schema迁移和发布

全部结构变化走编号迁移与校验和，先在恢复副本验证。启动服务迁移一次；采集器、策略、报告不能遇到缺列就自行ALTER。迁移号以仓库实际下一个未占用版本为准，本文不指定会冲突的SQL编号。

报告流程：完整run目录 → manifest声明所有产物和hash → 校验 → 发布锁中原子切换一个current指针 → 读者按指针读取整套内容。发布完成状态不得早于实际提交；失败页面不伪装执行绿灯。回滚也是版本指针操作，旧失败任务不能覆盖新成功任务。

## 4. 数据模型：保留历史证据，而不制造新的几百张表

下列是必须拥有清晰主键和写入者的逻辑对象，可按职责合并物理实现。结构化行情/资金/账户核心列采用具体类型；原始JSON用于原文与补充，不做不受约束的万能事实表。

| 逻辑对象 | 核心字段 | 修改规则 |
|---|---|---|
| `ingestion_batch` | batch_id、dataset_id、scope、started/finished、status、counts、hash | 状态受控转换；提交后内容固定 |
| `raw_observation` | observation_id、batch、endpoint、参数hash、received_at、payload_ref、payload_hash | 追加；重复接收保留事件但事实去重 |
| 标准化事实表 | instrument、event_time/period_end、known_at、source_revision、单位、定义、质量 | 新版本追加；最新表仅为投影 |
| `instrument_version` | 市场、代码、身份、上市退市、生效区间、known_at | 版本化，不用当前股票名单代替历史 |
| `theme_relation_version` | theme_id、instrument、relation_type、role、known_at、valid_from/to、证据 | 归属、当天原因与角色分开 |
| `input_manifest` | snapshot_id、asof、mode、事实/批次版本、代码/配置hash | 不可变，作为一次决策的输入集合 |
| `feature_snapshot` | instrument/theme、feature_version、值、缺失状态、manifest | 追加；与研究计算同定义 |
| `signal_event` | signal_id、strategy_version、state、asof、manifest、原因码 | 不可变事件；同股同日允许多次 |
| `account_snapshot` | account_id、snapshot_id、cash、positions、sellable、open_orders、asof、reconciled | 真实来源快照追加，不被策略清空 |
| `account_event` | event_id、账户、成交/费用/出入金/公司行为、更正引用 | 追加；更正不删除原事实 |
| `decision_certificate` | 输入/信号/账户/政策版本、许可、限制、有效期、阻塞 | 不可变；取消/过期通过新状态事件 |
| `reservation` | reservation_id、账户、决策、金额/数量/风险占用、状态 | 受控CAS/事务转换，防重复资金使用 |
| `operator_action` | 操作者、decision_id、确认/拒绝/备注、发生时间、幂等键 | 人工事实追加，自动流程无覆盖权 |
| `execution_event` | order/client_id、submit/ack/partial/fill/cancel/unknown、来源 | 与信号/人工点击严格区分 |
| `data_usage_event` | dataset/origin、feature/signal/decision、消费与增量作用 | 追加；用于价值核查而非收费调用计数 |
| `research_trial` | trial_id、冻结参数/数据/标签、拆分、成本、结果、不确定性 | 失败试验同样保留，不能只登记最佳 |

现金和数量计算使用明确固定精度数值，外部格式进入时验证有限性和范围。证券身份包含交易所，CSV按字符串读入；显示小数不等于内部精度。费用、价格步长、买卖单位和结算规则独立版本化，不全局假定所有市场100股、10%涨跌幅或同一税率。

### 4.1 时间合同是整个方案最重要的合同

统一注入TradingClock；存储可还原时区的时间，展示使用Asia/Shanghai。源事件时间、接收时间和已验证可用时间不得混同。预算/耗时用单调时钟，交易日/阶段用交易时钟与日历。

对市场观察，真实重放至少要求 `event_time <= decision_asof`、`received_at <= decision_asof`、`validated_available_at <= decision_asof`，以及修订版本在截止前已存在。对于已公告的未来解禁等计划事件，**生效时间可以晚于asof**；限制的是公告信息当时是否已知，不能机械地把所有未来生效事件都过滤掉。

定义两个绝不混淆的模式：

| 模式 | 可用性 | 可用于什么 |
|---|---|---|
| `system_replay` | 使用系统真实收到/验证过的版本 | 重现当时系统决定，验证实时影子链 |
| `historical_research` | 对缺少真实接收档案的数据声明保守发布时间假设与未知修订风险 | 研究假设，不声称原系统当时可执行 |

没有历史快照，就承认无法还原该过程。迁移时把旧数据标成“有原始时点证据”“仅日线/终态研究”“未知/隔离”；不能为通过回测而补写一个假的received_at。历史修订生成新研究结果，不覆盖旧决策。

### 4.2 事件顺序、重复与缺口

提交者为每个已接受事件分配单调的 `ingestion_seq`；重放按照“当时可用时间 + 提交序号”排序，源内顺序另保留。幂等键优先使用稳定源事件ID/修订号；缺少源ID时由数据集、证券、业务时点、规范化内容和修订策略构成，不能把同秒但不同内容的报价误去重。

乱序和晚到事实进入档案，但不会修改早先已经发出的信号；实时当前状态如何接纳修订由产品契约决定。批次完整性、水位和采样缺口显式记录：队列过载时只能按明确政策合并允许合并的快照，绝不能静默丢弃委托/成交/账户事件或把缺口假装成连续过程。

### 4.3 配置批准也是版本化事实

权益、模式TTL、策略阈值、账户风险预算与可执行证券范围分别有负责人、批准版本和生效时间。开发者可用 `test_only` 参数验收算法分支；生产加载器拒绝这类参数。参数变更使相关未执行证书重新评估，不能让旧额度在新政策下继续有效。

## 5. 数据产品计划：KPL和TuShare如何真正进入价值链

完整机器规格见 `data_products.yaml`。12项是能力划分，不代表12个接口或12项新采购，也不要求全部成为每次交易的必需条件。

| 产品 | 主要来源候选 | 首要消费者 | 增量价值假设 |
|---|---|---|---|
| DP01 基础行情/广度 | 已验证基础来源 | 市场和基础候选 | 免费基线与低成本全市场发现 |
| DP02 证券/交易参考 | TuShare、核实的券商/交易所参考 | 历史范围与硬风险 | 减少证券身份、状态和规则误用 |
| DP03 题材语义/角色 | KPL专题 | 核心候选、计划理由 | 区分长期归属与当天交易主线 |
| DP04 梯队/涨停/炸板 | KPL、TuShare专题 | 市场结构和同类样本 | 研究晋级、失败与题材持续性 |
| DP05 竞价最终结果 | TuShare stk_auction、合格KPL源 | 开盘前最后确认、开盘后计划 | 相对历史/同类的结果异常 |
| DP06 竞价过程 | 实测满足权益/时效的过程源 | 过程研究 | 只有能力真实存在才研究过程，首期非必须 |
| DP07 盘中资金过程 | KPL合格专题等 | 资金变化、触发/失效 | 同源区间变化而非累计排名 |
| DP08 新鲜报价/流动性 | 经过授权及时效验证的行情 | 确认时重检、持仓管理 | 可观察价格与交易资格约束 |
| DP09 历史日线/复权/指标 | TuShare | 样本分布、历史验证 | 建立可复现的研究基准 |
| DP10 已知风险事件 | TuShare财务/参考及授权公告 | 风险、已有持仓 | 数据不必提高选股收益也可降低漏报 |
| DP11 龙虎榜上下文 | KPL、TuShare等 | 次日假设与研究 | 已公开背景，不事后解释当日上午 |
| DP12 账户/执行事实 | 实际券商/真实导入 | 风险预算、结果验证 | 让“可执行”绑定真实账户而非空仓假设 |

### 5.1 不能忽略的三个外部接口事实

TuShare官方说明 `stk_auction` 为9:26—9:29可获取的竞价结果且需单独权限；`stk_auction_o` 是盘后更新。它们不是同一种实时能力，不能互为无条件替代。[S1][S2]

TuShare `kpl_list`提供KPL榜单，说明交付服务商不同不必然意味着原始来源独立。必须核实同源关系，不把同源三路数据变成三票一致确认。[S3]

`moneyflow`有明确金额/成交量单位和自有净流入定义；官方强调净流入不能简单把大小单总和相减。`limit_list_d`也有不提供ST统计等范围边界。因此归一单位不代表指标含义相同，缺范围数据也不能简单算成接口失败。[S4][S5]

KPL网关的路径清单仅用于需求和消费者追踪，不足以证明实际购买了逐笔、完整盘口或低延迟能力。WP04须按实际合同和样本确认；本轮不依据“接口名含L2”作能力承诺。

### 5.2 数据失效按模式，而不是一把全局大锁

必需输入、可选输入、研究输入分别注册。每股报价和账户必须满足本次决策前提；但缺一个可选龙虎榜上下文不能阻塞所有持仓观察。某模式需要完整广度时使用可追溯的适用分母；不能因为抓不到某些股票就把它们移出分母。

现有99.5%等门槛需要按真实口径重新确认，不能为出信号调低，也不能照搬成所有模式唯一门槛。缺失的必需输入导致该模式/该股阻塞；缺可选输入使用事先验证的降级版本，不能临时切掉特征却沿用原模型和阈值。

### 5.3 采集资源分配

先保证账户与已有持仓，再保证活跃计划与候选，然后是全市场发现；历史和长模型任务最后。按数据源共享请求去重、并发、配额和失败预算。对可消失的实时过程，在授权和容量范围内尽早独立留档，避免代码重构期间继续丢失无法补采的历史。

所有频率基于实际权益和模式窗口配置，配置中保留null表示待核实，不自动填一个“看起来实时”的数值。执行可用的必要条件是总延迟（源更新/传输/提交/计算/人工）不大于模式有效窗口；实测不满足则仅研究。

## 6. 特征与交易模式：不要再扩大一个总分公式

`feature_registry.yaml`包含24个初始研究特征定义。它们不是24条已验证买入规则，也不保证都保留。

| 特征组 | 定义示例 | 替代的问题 |
|---|---|---|
| 市场/梯队 F01–F03 | 广度、上一日梯队截至当前的晋级、失败队列表现 | 只按涨停数量给情绪标签 |
| 题材/角色 F04–F06 | 相对强度、参与广度/集中、核心角色持续 | 把概念成员等同当天主线，最高板等同最佳候选 |
| 竞价 F07–F10 | 自身历史金额比、前日成交额占比、同类分位、核心一致性 | 绝对金额大就判强 |
| 资金/盘口 F11–F16 | 同源区间净额、区间成交额比例、价量/资金分歧、报价年龄、可见流动性、过程路径 | 累计求和、择最大值、假定成交 |
| 风险/账户 F17–F22 | 可交易性、已知事件、已披露龙虎榜、剩余额度、可卖量、原始来源一致性 | 零仓位风控、未知风险当零、同源重复确认 |
| 样本/容量 F23–F24 | 冻结规则的同类样本分布、同类流动性分位 | 无校准概率、无容量的高分榜单 |

### 6.1 第一条策略的完整规格

名称：`theme_core_auction_follow_v1`。当前状态：research_only。证券范围先限于参考规则、账户权限和时效均验证过的白名单；未认证市场/特别处理/新股条件不自动执行。不要把这当作对某类股票的投资推荐，而是开发能力边界。

**D日收盘：** 按可知题材、梯队及已完成日线选观察范围。记录题材、角色、选择理由、反对证据、候选进入时间、取消条件。历史同类分布仅给样本和区间，不把未校准的比例写为“胜率保证”。候选集合不能仅来源于后来被确认为龙头的成功名单。

**D+1竞价结果确认：** 使用实际收到结果，计算F07–F10。结果没到就等待；到达时已经错过有效窗口则过期。只有最终结果时不做撤单、竞价承接过程等无证据归因。

**开盘后：** 根据提前冻结的价格区间、题材支持、个股资金/成交条件进入triggered，或者因条件失效进入invalidated。具体条件与阈值必须在训练/验证区间选取并登记后冻结；为了让框架运行的测试参数只能标fixture，不能当实盘默认值。

**数量与人工确认：** 调用DecisionService。没有账户、额度、可信报价或已批准规则，允许查看但不产生真实执行许可。确认时重新校验而非使用旧卡状态，并原子预占额度。

**持仓管理：** 真实成交或新快照进入后，优先评估持有理由、主题变化和风险。退出条件与当前可卖量分开表达：条件失效并不等于此刻一定可以卖出，更不等于可按指定止损价成交。系统外操作必须重新对账。

**复盘：** 分开记录策略条件、人工处理、券商事实和事后研究结果。未做原因含未触发、数据不足、账户限制、拒绝、错过价格、实际未成交等；不能把未成交机会记为真实收益。

### 6.2 其他模式如何进入

| 模式 | 实施前必须有的证据 | 不满足时 |
|---|---|---|
| 半路/开盘后延续 | 模式窗口内的价格/题材/成交证据及账户 | 观察，不临时放松 |
| 低吸 | 支撑/失效区间定义、可知主题、可卖/持有风险，独立样本 | 研究，不复用追强阈值 |
| 回封 | 足够密度的实际开板/回封路径与成交限制 | 日线终态不足以声称回测可成交 |
| 打板 | 经实测支持的更新频率/延迟和流动性；排队模型能力明确 | 数据不达标则禁用执行，不能靠轮询宣传实时 |

每个模式必须同时交付入场、失效、已有持仓处理和失败恢复。模型只提供支持/反对证据，不绕过硬风险。没有证据的市场因果推断以“解释/假设”标注。

## 7. 真实账户与统一决策：执行级的底线

### 7.1 账户来源和未知处理

第一版可以从真实导出或经过明确确认的人工快照开始，但必须包含时间、现金、数量、可卖、未完成委托和控制总额。人工导入不是持续实时账户，过期或发生系统外操作后不能继续按原快照批准。

账户快照是事实，策略篮子是建议。两者分库逻辑/命名和权限，绝不相互覆盖。实际净资产与账本推导对账不一致时先阻塞新增执行，不自动把差额“修成一致”。开仓预算需要扣掉真实持仓、冻结委托、其他计划预占及费用余量。

建议的单笔数量上限是按适用交易单位向下取整后的各项上限最小值：可用现金、单股剩余额度、题材剩余额度、总风险额度、已验证容量约束。具体政策预算由用户批准，本文不预设一个会被误当真实风险偏好的百分比。止损距离得到的风险估计必须另考虑跳空、无法及时卖出的压力场景，不表述为保证损失上限。

### 7.2 三类状态分开，但最终许可只有一个权威

策略状态回答是否触发；人工计划状态回答人是否确认；委托/成交状态回答外部到底发生什么。它们不相互冒充。最终“此刻允许哪些动作”只由DecisionService组合并发出版本化证书，其他模块只能读取。

真实执行资格必须同时满足：模式已批准、必需数据合格、信号仍有效、账户新鲜且对账、风险批准、人工确认、确认后重新校验、额度已预占、无硬阻塞/杀开关。券商写入还需要相关授权和适用合规检查。shadow中即使纸面全部条件满足，字段也只能叫hypothetical_ready，真实execution_ready保持false。

完整证书字段样例见 `decision_certificate_example.json`。它是一个刻意阻塞的设计示例，不是生产交易记录。它绑定信号、输入manifest、账户快照、策略/风险/构建版本、报价、有效期、允许动作、最大数量/金额、预占、确认和阻塞原因。

证书保存的是**签发时的许可**。用户查看/确认时，由同一DecisionService根据当前时钟、是否被撤销、关联输入/账户版本和预占状态生成有效许可；不能把数据库里曾经为true的execution_ready直接当成当前允许。历史回放保留原签发时判断，当前界面明确显示评估时点与过期原因。

### 7.3 预占、幂等和UNKNOWN

两个计划不能各自用同一份“剩余现金”通过。确认与额度预占需要在同一账户版本下事务性完成；同一确认请求重试不重复预占。人工报告已执行而成交未核实，应保留未知状态，不能一到TTL就自动释放资金给下一笔。

若未来接券商：本地持久化提交意图后发送；超时只能表明没收到结果，不表明没下单。必须查单/对账；不具备可验证幂等/查询能力的接口由人工消解未知，不能盲目重发。撤单请求不等于撤单成功，杀开关不等于已平仓。

## 8. 回测与付费价值实验

### 8.1 先修资金数学与数据时点

使用同一策略纯函数和相同风险规则，替换为现金/数量/费用/公司行为/可卖日期账本。每日或所需观察频率估值，未变现跌幅进入回撤。原始执行价与研究复权价分离，不能同时把现金分红和同一复权调整重复计收益。

日线只能支持它能识别的研究，不能制造分钟内先后顺序或回封排队成交。缺退出报价/停牌/封死时明确记录估值年龄、未平仓暴露和无法成交，而不是用理想收盘价强制结算。

### 8.2 四组对照须有共同安全底座

设C为不允许在真实运行删除的共同安全约束，F为经过明确登记的低成本决策输入。运行C+F、C+F+K、C+F+T、C+F+K+T。验证结果所用未来标签可作为共同评估资料，但不能混入任一决策输入。

某项必需安全参考只能通过TuShare可靠取得时，应披露它属于共同底座C；不能把这个配置宣传成“严格零付费基线”。另外的TuShare专题/研究特征才算T的增量。不能为了显示付费风险数据有用而在真实对照中删除必要风险检查。

分别比较固定共同候选池与完整可变化候选池。前者测试过滤/时机，后者测试发现能力。每组独立纸面账户、同预算、同延迟与成本模型，不共享真实账户额度。

### 8.3 价值指标与统计边界

主要指标预登记，不在结果出来后改成好看的那个。至少记录机会覆盖与误报、实际可成交比例、风险事件遗漏、资金与主题集中、成本后收益/回撤、操作耗时、源故障与恢复。以相同交易日/题材聚类处理相关性，保留多次试验次数、失败结果和不确定区间。

区分“数据被消费”“数据改变决策”“数据带来改善”。一个接口长期只用于研究或恢复仍可有价值；改变很多决策也可能是有害。停用、降频、仅容灾和继续保留都是合法实验结论。

20个连续交易日仅作为建议运行稳定性初筛，不足以证明盈利。经济价值的最小可接受改善、样本量/功效设计、保留集和各阶段覆盖由研究计划事先确定；样本不足要显示inconclusive，不能为按期验收强行给正结论。

### 8.4 Qlib单独验收

label_end_time和标签可用时点必须进入拆分；训练/验证相邻时删除跨界标签样本；最终保留测试不能用于早停或选模型。特征热身按交易观测，部分复权缺失不填1，导出用不可变版本与原子指针，CSV保留代码身份。模型保持影子，只有独立研究与批准后才讨论升级，不因框架接上而增加实盘权重。[A1]

## 10. 迁移、灰度、回滚和退役

### 10.1 四段迁移

第一段保存已验证备份，记录旧代码和库版本；旧系统降为研究参考，保护人工事实。第二段新链消费同一份原始扇出数据，避免重复收费请求；只写自己的库和投影。第三段新链在纸面账户与真实只读账户检查中影子运行，对差异分“旧算法错误修复”“新能力增量”“新缺陷”，不要求新旧错误结果相同。第四段按模式/证券白名单灰度切换人工计划，随后封锁旧写入入口并退役旧弱ready。

迁移验收有四种证据：行数/唯一键/控制总额；输入与结果可重放；人工事实和关联完整；回滚后真实成交不丢失。每个迁移批次有mapping和checkpoint，非法旧行隔离，不用默认值修成合格。

### 10.2 回滚只能回滚代码和投影，不能抹去交易事实

触发回退的情况包括硬门禁矛盾、账户对账差异、报价被伪刷新、不可追溯决策、重复外部动作和发布混版。动作是关闭新开仓、撤销尚未执行许可、保留未知委托和预占、人工对账、恢复已批准v2稳定版本或只读观察。

不能将数据库整体覆盖回昨日，因为期间可能发生真实交易。旧版本不安全执行链也不能当作故障兜底。必要结构变化用向前修复与兼容投影，保留append-only事实。

### 10.3 退役条件

旧表/脚本的全部消费者已迁移；写入者清单证明没有旧路径改新事实；完整发布周期内无旧调用；兼容接口有关闭测试；完成备份与恢复验证。删除源码不是主要收益，减少相互矛盾的权威和维护入口才是。

## 11. 验收、运维、成本和权限

`acceptance_catalog.yaml`有48个行为场景。它们目前是待实现测试规格，不是48个已经通过的测试。原审计的10个独立反例也不能冒充全仓回归。[A1]

| 验收层 | 必须提供的证据 |
|---|---|
| 单元/金标准 | 数值语义、状态不变量、手算资金结算 |
| 数据契约 | 实际脱敏样本、单位、时点、覆盖、修订、错误响应 |
| 端到端 | 真实结构fixture跨收盘/竞价/盘中/持仓/复盘，禁用外部写入 |
| 真实平台 | Windows双进程锁、异常退出、权限未知、发布恢复 |
| 实际源影子 | 真正授权的实际数据时效、可用性、配额与消费者，不用mock顶替 |
| 经济价值 | 冻结独立对照、可成交与成本口径、样本不确定性，允许无改善 |
| 可选真实路由 | 券商测试/受控环境、幂等、未知状态、部分成交、撤单结果和人工批准 |

硬不变量要求零违反：任何硬阻塞没有真实许可；未知账户不当空仓；未来和晚到数据不污染过去；相同输入可重放；人工事实不覆盖；现金和数量守恒；发布完整；未知外部动作不盲重发。

建议运维记录每项真实数据产品的源年龄/接收年龄、成功/部分/失败、覆盖分母、请求成本、消费者，以及队列积压、决定耗时、证书过期、账户对账、通知处理。运行成功、数据足够、策略触发、账户允许、用户确认、外部成交六个状态独立清楚，不把退出码0展示成全部就绪。

原始数据、账户、模型与普通日志分权限；凭据从受控环境读取，日志脱敏，不写报告/模型提示。操作API本地认证、Origin/CSRF、请求大小和速率限制，SQL白名单/参数化、HTML转义、无任意文件路径；远程开放另外评审。带工具调用意图的外部新闻仍只是数据。模型artifact只加载本项目批准且hash核验的版本，不反序列化未知来源的pickle；模型输出不直接执行或修改文件/交易配置。

存储保留基于实际许可、监管适用性和用户批准政策确定，不能用“只留30次运行”删除长期决策或未平仓证据。昂贵重算和历史补采有配置预算、熔断和恢复点；已有持仓监控优先。费用台账区分接口成本、计算/存储、人工维护与有证据的容灾价值，不能把估算省钱当现金收入。

上交所现行程序化交易规则涉及报告、交易行为与信息系统管理。真实计划/委托的适用要求须结合实际使用方式与券商确认；人工确认不是当然豁免。数据的个人研究许可不能自动覆盖商业化或对外分发。此处是实施前置核查项，不是对具体账户法律资格的确认。[S7]

## 12. 给开发者/Codex的执行协议

开发不依赖聊天记忆。把本包作为版本化规格，在仓库新建docs/v2；每次任务开始读取主方案、DECISIONS、STATUS、当前工作包及其原问题映射。重新核对实际HEAD；有其他未提交改动时保护它们，不强制reset。

每次只做一个依赖已满足的工作包或一个明确子任务；先写能暴露问题的回归，再改最小所需代码，再进行相关和全链验收。不是修完每行就跑全仓重型任务，也不是一口气重写全部。公共契约变化先记设计决策和迁移，再更新消费者。

阶段验收保存：实现提交/构建hash、变更路径、数据fixture标识、实际执行命令、退出码、测试数量与结果、未验证场景、原问题关闭证据、回滚验证和负责人批准。相同人可以承担多个角色，但实现与验收应有独立复核记录。

**禁止：**为通过测试删除断言；把真实源错误改成空列表后记成功；降低门槛只为多出信号；批量用0/1补未知账户/复权；伪造历史时间或成交；用旧CI证明新代码；调用接口目录中的非只读行为；启用真实委托；把尚未核实权益写成已验证。

连续交易/收益评估期间冻结代码、策略、数据和实验版本。需要修复时终止或分段登记该试验，使用新trial_id，不在同一结果里隐瞒中途改参数。

详细启动说明、每包提交模板和完成定义见 `CODEX_IMPLEMENTATION.md`。文件中的CLI名称是拟实现接口约定，不是声称现在仓库里已存在。

## 13. 最终放行标准与继续投入判断

第一关是“不会误导或破坏”：核心正确性、未知账户、不可变时点、运行锁和资金结算必须过。第二关是“用户确实能完成闭环”：第一策略和已有持仓被同一份可信状态管理。第三关是“付费数据可解释地产生价值”：独立对照支持改进或能证明可靠性/时间成本价值，而不是只是多了一些字段。

若付费数据无增益，允许保留为历史验证或恢复源、降低频率/权益、停止无消费者的扩张。若某类实时权益/时效不满足，保留该模式研究并继续改进可行模式，不将能力缺失包装成实时执行。

**最终成果不是一个更大的stock_data，而是一个每次决定都能解释、复现、约束并评价投入产出的系统。**
